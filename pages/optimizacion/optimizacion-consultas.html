Optimización de consultas SQL

Escribir consultas SQL eficientes es tan importante como tener buenos índices. Una consulta mal formulada puede ignorar los mejores índices y saturar el servidor. En esta página verás patrones concretos para escribir SQL rápido y evitar los errores más comunes que degradan el rendimiento.

1. Evita SELECT *

SELECT * obliga a MySQL a leer todas las columnas de la tabla, incluido el contenido de columnas grandes como TEXT o BLOB. Además, impide que el índice cubra la consulta (covering index). Siempre especifica solo las columnas que necesitas.

SQL — Malo vs. Bueno
-- ❌ Lento: trae todas las columnas
SELECT * FROM usuarios WHERE email LIKE '%@gmail.com';

-- ✅ Rápido: solo las columnas necesarias
SELECT id, nombre, email FROM usuarios WHERE email LIKE '%@gmail.com';

2. EXISTS vs. IN

Cuando la subconsulta externa filtra por una columna de la tabla interna, EXISTS suele ser más eficiente porque MySQL puede detenerse al encontrar la primera coincidencia. IN evalúa todos los registros de la subconsulta primero.

SQL
-- ❌ IN materializa toda la subconsulta
SELECT * FROM clientes c
WHERE c.id IN (SELECT cliente_id FROM pedidos WHERE total > 1000);

-- ✅ EXISTS corta al encontrar la primera coincidencia
SELECT * FROM clientes c
WHERE EXISTS (SELECT 1 FROM pedidos p WHERE p.cliente_id = c.id AND p.total > 1000);

3. LIKE con prefijo fijo

Un LIKE 'abc%' puede usar índices, pero LIKE '%abc' o LIKE '%abc%' nunca pueden usar índices porque el comodín está al inicio.

SQL — Índice usable vs. no usable
-- ✅ Usa índice (prefijo fijo)
SELECT * FROM productos WHERE nombre LIKE 'lap%';

-- ❌ No usa índice (comodín al inicio)
SELECT * FROM productos WHERE nombre LIKE '%top';

4. No apliques funciones a columnas indexadas

Usar YEAR(), DATE(), LOWER() o cualquier función directa sobre la columna hace que el índice sea inservible. Se llama "no sargable".

SQL
-- ❌ No sargable: fuerza full table scan
SELECT * FROM pedidos WHERE YEAR(fecha) = 2024;

-- ✅ Sargable: usa índice en fecha (si existe)
SELECT * FROM pedidos WHERE fecha >= '2024-01-01' AND fecha < '2025-01-01';

5. JOINs óptimos

En un JOIN, la tabla con el filtro más restrictivo debe ir primero (MySQL suele optimizarlo automáticamente, pero el orden lógico importa). Asegúrate de que las columnas del JOIN estén indexadas.

SQL
-- Asegura índices en ambas tablas
CREATE INDEX idx_pedidos_cliente ON pedidos(cliente_id);
CREATE INDEX idx_clientes_id ON clientes(id);

-- JOIN eficiente: cliente_id está indexado
SELECT c.nombre, SUM(p.total) AS gasto
FROM clientes c
JOIN pedidos p ON p.cliente_id = c.id
WHERE c.activo = 1
GROUP BY c.id;

6. LIMIT con subconsultas para paginación

En tablas grandes, LIMIT 100000, 20 recorre y descarta 100.000 filas. Una técnica más eficiente es usar una subconsulta que recorra solo el índice.

SQL — Paginación eficiente
-- ❌ Lento: OFFSET alto recorre muchas filas
SELECT * FROM pedidos ORDER BY id LIMIT 100000, 20;

-- ✅ Rápido: subconsulta sobre índice
SELECT p.* FROM pedidos p
INNER JOIN (SELECT id FROM pedidos ORDER BY id LIMIT 100000, 20) AS sub
ON p.id = sub.id;

Usa EXPLAIN antes y después de cada optimización para confirmar que el plan de ejecución mejoró. Sin medición, no hay optimización.

Checklist de optimización: (1) ¿Hay SELECT *? → cámbialo. (2) ¿Los filtros usan funciones sobre la columna? → hazlos sargables. (3) ¿Las columnas de JOIN tienen índice? → créalo. (4) ¿Hay LIKE con comodín inicial? → evalúa FULLTEXT. (5) ¿El OFFSET es alto? → aplica keyset pagination.
