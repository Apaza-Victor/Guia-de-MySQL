Particionamiento de tablas

El particionamiento divide una tabla grande en fragmentos físicos más pequeños llamados particiones, cada uno con su propio segmento de datos. Las consultas siguen viendo una sola tabla lógica, pero MySQL puede saltarse particiones enteras (partition pruning) cuando las condiciones del WHERE se alinean con la clave de partición. El resultado: lecturas más rápidas y mantenimiento más ágil.

Tipos de particionamiento

MySQL 8.0 soporta cuatro tipos principales de particionamiento. La elección depende de la naturaleza de tus datos y de los patrones de consulta.

PARTITION BY RANGE

Divide los datos en intervalos de valores. Ideal para datos con una dimensión temporal (fechas, años).

SQL — Partición por RANGE
CREATE TABLE pedidos (
    id INT NOT NULL,
    cliente_id INT,
    total DECIMAL(10,2),
    fecha DATE,
    PRIMARY KEY (id, fecha)
) PARTITION BY RANGE (YEAR(fecha)) (
    PARTITION p_antes_2022 VALUES LESS THAN (2022),
    PARTITION p_2022 VALUES LESS THAN (2023),
    PARTITION p_2023 VALUES LESS THAN (2024),
    PARTITION p_2024 VALUES LESS THAN (2025),
    PARTITION p_futuro VALUES LESS THAN MAXVALUE
);

PARTITION BY LIST

Asigna filas a particiones según una lista de valores discretos. Útil para categorías o regiones geográficas.

SQL — Partición por LIST
CREATE TABLE clientes (
    id INT NOT NULL,
    nombre VARCHAR(100),
    region VARCHAR(20),
    PRIMARY KEY (id, region)
) PARTITION BY LIST COLUMNS(region) (
    PARTITION p_norte VALUES IN ('Norte', 'Noreste', 'Noroeste'),
    PARTITION p_centro VALUES IN ('Centro', 'Centro-Occidente'),
    PARTITION p_sur VALUES IN ('Sur', 'Sureste', 'Suroeste')
);

PARTITION BY HASH

Distribuye los datos uniformemente aplicando una función hash a la clave de partición. Ideal cuando no hay una agrupación natural clara.

SQL — Partición por HASH
CREATE TABLE logs (
    id INT NOT NULL AUTO_INCREMENT,
    severidad TINYINT,
    mensaje TEXT,
    creado_en TIMESTAMP,
    PRIMARY KEY (id)
) PARTITION BY HASH(id) PARTITIONS 8;

PARTITION BY KEY

Similar a HASH pero usa el hash interno de MySQL (MD5-like). La clave debe ser parte de la PRIMARY KEY.

SQL — Partición por KEY
CREATE TABLE sesiones (
    sesion_id CHAR(36) NOT NULL,
    usuario_id INT,
    datos JSON,
    PRIMARY KEY (sesion_id)
) PARTITION BY KEY() PARTITIONS 4;

Cuándo particionar

Caso de usoRecomendación
Tablas > 10 millones de filas (InnoDB)Considera particionar por rango de fechas
Purgar datos antiguos regularmenteTRUNCATE PARTITION es instantáneo vs. DELETE lento
Datos con segmentación natural (región, año)RANGE o LIST según el caso
Carga uniforme sin agrupación naturalHASH o KEY
Tablas pequeñas (< 1M filas)No particiones — la sobrecarga no lo justifica

Ventajas del particionamiento

El particionamiento ofrece beneficios claros en rendimiento y administración:

  • Partition Pruning: MySQL ignora particiones enteras cuando el WHERE filtra por la clave de partición.
  • Mantenimiento selectivo: puedes reparar, optimizar o truncar una partición sin afectar al resto.
  • Archivado eficiente: mueve particiones completas a tablas de archivo con ALTER TABLE ... REORGANIZE PARTITION.
  • Paralelismo: algunas operaciones (como escaneos grandes) pueden procesar particiones en paralelo.

Limitaciones importantes

  • La clave de partición debe ser parte de todas las claves únicas (incluida la PRIMARY KEY).
  • No soporta claves foráneas en tablas particionadas.
  • El número máximo de particiones es 8192.
  • No se pueden usar índices FULLTEXT o SPATIAL en tablas particionadas.
  • ALTER TABLE en tablas particionadas puede requerir reconstruir todas las particiones.

ALTER TABLE con particiones

SQL — Gestión de particiones
-- Agregar una partición
ALTER TABLE pedidos ADD PARTITION (
    PARTITION p_2025 VALUES LESS THAN (2026)
);

-- Eliminar una partición (borra los datos también)
ALTER TABLE pedidos DROP PARTITION p_antes_2022;

-- Dividir una partición en dos
ALTER TABLE pedidos REORGANIZE PARTITION p_futuro INTO (
    PARTITION p_2025 VALUES LESS THAN (2026),
    PARTITION p_futuro VALUES LESS THAN MAXVALUE
);

-- Verificar particiones
SELECT TABLE_NAME, PARTITION_NAME, TABLE_ROWS
FROM INFORMATION_SCHEMA.PARTITIONS
WHERE TABLE_SCHEMA = 'midb' AND TABLE_NAME = 'pedidos';

El partition pruning solo funciona si la consulta filtra directamente por la clave de partición. Por ejemplo, si particionas por YEAR(fecha), la consulta WHERE fecha BETWEEN '2024-01-01' AND '2024-12-31' NO hará pruning porque MySQL no puede deducir que YEAR(fecha) = 2024. Usa WHERE fecha >= '2024-01-01' AND fecha < '2025-01-01' después de particionar por RANGE COLUMNS(fecha).

Elegir la clave de partición incorrecta es el error más común. La clave debe: (1) estar presente en la mayoría de los WHERE, (2) distribuir los datos uniformemente (evitar particiones "calientes" que concentren la mayoría de los datos), y (3) permitir pruning. Una mala elección puede hacer que las consultas sean más lentas que sin particionamiento.
