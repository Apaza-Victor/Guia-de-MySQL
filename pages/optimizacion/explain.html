EXPLAIN — Analizando planes de ejecución

EXPLAIN es la herramienta más importante para optimizar consultas en MySQL. Te muestra cómo el optimizador planea ejecutar una consulta: qué índices usará, en qué orden unirá las tablas y cuántas filas estima examinar. Dominar EXPLAIN te permite detectar cuellos de botella y verificar si tus índices se están aprovechando realmente.

Sintaxis básica

Antepón EXPLAIN a cualquier SELECT (también funciona con INSERT, UPDATE, DELETE y REPLACE). MySQL devolverá una tabla con el plan de ejecución estimado.

SQL
EXPLAIN SELECT u.nombre, COUNT(p.id) AS total_pedidos
FROM usuarios u
LEFT JOIN pedidos p ON u.id = p.usuario_id
WHERE u.activo = 1
GROUP BY u.id
ORDER BY total_pedidos DESC;

Columnas del plan de ejecución

Cada fila del resultado representa una operación o acceso a una tabla. Las columnas más relevantes son:

ColumnaSignificado
idNúmero de paso en la ejecución; valores iguales indican que las tablas se unen en el mismo paso.
select_typeTipo de consulta: SIMPLE, PRIMARY, SUBQUERY, DERIVED, UNION, etc.
tableNombre de la tabla o alias usado en este paso.
partitionsParticiones involucradas (si aplica).
typeTipo de acceso al dato. Es la columna más crítica para detectar lentitud.
possible_keysÍndices que MySQL consideró como candidatos.
keyÍndice que MySQL eligió realmente (NULL si no usó ninguno).
key_lenLongitud en bytes del índice usado.
refColumnas o constantes comparadas contra el índice.
rowsFilas estimadas que MySQL cree que debe examinar.
filteredPorcentaje estimado de filas que pasarán el filtro WHERE.
ExtraInformación adicional: Using index, Using where, Using filesort, Using temporary.

Tipos de acceso (type)

La columna type revela la eficiencia del acceso. Ordenados de peor a mejor rendimiento:

typeRendimientoDescripción
ALL⚠️ PésimoRecorre toda la tabla (full table scan). Señal de alerta en tablas grandes.
index⚠️ MaloRecorre todo el índice (full index scan), similar a ALL pero sobre el índice.
range✅ AceptableRecorre un rango del índice (BETWEEN, >, LIKE 'abc%').
ref✅ BuenoBúsqueda por un valor no único del índice.
eq_ref✅ ExcelenteBúsqueda por clave única/primaria en JOINs.
const✅ ÓptimoBúsqueda por clave primaria con constante. Máxima velocidad.

Ejemplo práctico: consulta lenta vs. optimizada

Partimos de una tabla pedidos sin índice en cliente_id.

SQL — Sin índice → ALL
EXPLAIN SELECT * FROM pedidos WHERE cliente_id = 42;
-- type: ALL, rows: 500000, Extra: Using where

Agregamos un índice:

SQL
CREATE INDEX idx_pedidos_cliente ON pedidos(cliente_id);
SQL — Con índice → ref
EXPLAIN SELECT * FROM pedidos WHERE cliente_id = 42;
-- type: ref, key: idx_pedidos_cliente, rows: 12, Extra: NULL

El cambio es drástico: de 500.000 filas estimadas a solo 12. El índice redujo el costo en varios órdenes de magnitud.

Si ves type: ALL con rows elevado (> 10.000), estás ante un full table scan. Revisa si falta un índice o si el WHERE no es sargable (usa funciones sobre la columna indexada).

La columna Extra puede mostrar Using filesort o Using temporary, que indican ordenaciones y tablas temporales en disco. Ambos penalizan el rendimiento y suelen resolverse con índices compuestos adecuados.

EXPLAIN EXTENDED y FORMAT

MySQL 8.0+ admite EXPLAIN FORMAT=JSON para obtener el plan enriquecido con costos y estadísticas. También puedes usar EXPLAIN ANALYZE (MySQL 8.0.18+) para ejecutar la consulta real y mostrar tiempos de ejecución por paso.

SQL — Formato JSON
EXPLAIN FORMAT=JSON
SELECT * FROM pedidos WHERE cliente_id = 42\G
