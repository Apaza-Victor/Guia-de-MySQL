Buenas prácticas profesionales

Esta guía reúne las mejores prácticas para diseñar, mantener y operar bases de datos MySQL en entornos profesionales. Aplicarlas consistentemente mejora el rendimiento, la seguridad y la mantenibilidad del sistema.

Nombrado de bases de datos, tablas y columnas

Un buen nombrado hace que el esquema sea autodocumentado y reduce la confusión en equipos grandes.

SQL
-- Buenas prácticas de nombrado
-- BD: snake_case, descriptiva
CREATE DATABASE ecommerce_ventas;

-- Tablas: plural, snake_case
CREATE TABLE productos_categorias ( ... );

-- Columnas: snake_case, sin prefijos redundantes
-- Mal:  nombre_producto (la tabla ya es productos)
-- Bien: nombre

-- Claves foráneas: tabla_origen_id
CREATE TABLE pedidos (
    id INT AUTO_INCREMENT PRIMARY KEY,
    usuario_id INT NOT NULL,
    FOREIGN KEY (usuario_id) REFERENCES usuarios(id)
);

-- Índices: idx_tabla_columna
CREATE INDEX idx_pedidos_usuario_id ON pedidos(usuario_id);

Elegir tipos de datos correctos

Usar el tipo de dato adecuado ahorra espacio y mejora el rendimiento. Cada byte cuenta cuando trabajas con millones de filas.

SQL
-- Enteros: TINYINT (1 byte), SMALLINT (2), MEDIUMINT (3), INT (4), BIGINT (8)
CREATE TABLE ejemplo (
    edad TINYINT UNSIGNED,          -- 0-255, 1 byte
    poblacion MEDIUMINT UNSIGNED,   -- 0-16M, 3 bytes
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY  -- IDs grandes
);

-- Decimales: DECIMAL para precisión exacta, FLOAT/DOUBLE para aproximada
CREATE TABLE finanzas (
    precio DECIMAL(10,2) NOT NULL,  -- 10 dígitos, 2 decimales
    tasa FLOAT                      -- Aproximado, suficiente para estadísticas
);

-- Texto: CHAR vs VARCHAR
CREATE TABLE usuarios (
    genero CHAR(1),                -- Fijo: 1 carácter
    email VARCHAR(255) NOT NULL    -- Variable: solo almacena lo usado
);

-- Fechas: DATE, DATETIME, TIMESTAMP
CREATE TABLE eventos (
    fecha_evento DATE,              -- Solo fecha
    created_at DATETIME,            -- Fecha + hora
    updated_at TIMESTAMP            -- Fecha + hora, auto-actualizable
);

Siempre usar NOT NULL cuando corresponda

NULL complica las consultas, ocupa espacio adicional y puede dar resultados inesperados en comparaciones y agregaciones.

SQL
-- Preferir NOT NULL + valor por defecto
CREATE TABLE clientes (
    nombre VARCHAR(100) NOT NULL,
    email VARCHAR(255) NOT NULL,
    telefono VARCHAR(20) NOT NULL DEFAULT '',
    activo BOOLEAN NOT NULL DEFAULT TRUE
);

-- NULL solo cuando tenga significado real (ej: fecha de baja si no aplica)
CREATE TABLE suscripciones (
    id INT AUTO_INCREMENT PRIMARY KEY,
    usuario_id INT NOT NULL,
    fecha_baja DATE NULL  -- NULL significa "aún activo"
);

Índices estratégicos

Los índices aceleran las lecturas pero ralentizan las escrituras. Indexa con intención, no por inercia.

SQL
-- Indexar columnas usadas en WHERE, JOIN y ORDER BY
CREATE INDEX idx_pedidos_estado ON pedidos(estado);

-- Índices compuestos: ordenar por selectividad (mayor primero)
CREATE INDEX idx_ubicacion ON clientes(pais, ciudad, codigo_postal);

-- No indexar columnas con baja selectividad (ej: sexo con M/F)
-- No indexar columnas que raramente aparecen en filtros

-- Verificar índices existentes
SHOW INDEX FROM pedidos;

-- Monitorear índices no usados (desde Performance Schema)
SELECT * FROM sys.schema_unused_indexes;

Normalizar sin exagerar

La normalización elimina redundancia, pero en exceso puede perjudicar el rendimiento por la cantidad de JOINs necesarios.

NivelDescripciónCuándo aplicar
1FNValores atómicos, sin grupos repetitivosSiempre
2FNDependencia total de la clave primariaSiempre
3FNSin dependencias transitivasCasi siempre
DesnormalizaciónDuplicar datos para evitar JOINsReportes, data warehouses, lecturas masivas

Usar transacciones

Toda operación que involucre múltiples escrituras debe ejecutarse dentro de una transacción para garantizar la consistencia.

SQL
START TRANSACTION;
    UPDATE cuentas SET saldo = saldo - 100 WHERE id = 1;
    UPDATE cuentas SET saldo = saldo + 100 WHERE id = 2;
    INSERT INTO movimientos (cuenta_id, tipo, monto) VALUES (1, 'transferencia_egreso', 100);
    INSERT INTO movimientos (cuenta_id, tipo, monto) VALUES (2, 'transferencia_ingreso', 100);
COMMIT;
-- Si algo falla, ROLLBACK deshace todo

Prepared statements

Las consultas parametrizadas previenen inyección SQL y mejoran el rendimiento al reutilizar planes de ejecución.

SQL
-- Prepared statement en MySQL
PREPARE stmt FROM 'SELECT * FROM usuarios WHERE email = ? AND activo = ?';
SET @email = 'ana@email.com';
SET @activo = 1;
EXECUTE stmt USING @email, @activo;
DEALLOCATE PREPARE stmt;

-- En código (PHP con PDO)
-- $stmt = $pdo->prepare('SELECT * FROM usuarios WHERE email = ?');
-- $stmt->execute(['ana@email.com']);

Backups automáticos

Un backup que no se prueba periódicamente no es un backup. Automatiza y verifica las restauraciones.

Shell
# Backup lógico con mysqldump (todas las BD)
mysqldump -u root -p --all-databases --routines --triggers --events > full_backup.sql

# Backup físico con MySQL Enterprise Backup o XtraBackup
# xtrabackup --backup --target-dir=/backups/2025-01-15

# Automatizar con cron (Linux)
# 0 2 * * * /usr/bin/mysqldump -u root -p'pass' --all-databases | gzip > /backups/db_$(date +\%Y\%m\%d).sql.gz

Monitoreo: Slow Query Log y Performance Schema

El monitoreo continuo permite detectar cuellos de botella antes de que afecten a los usuarios.

SQL
-- Activar Slow Query Log
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 2;      -- Consultas que tardan más de 2 segundos
SET GLOBAL slow_query_log_file = '/var/log/mysql/slow.log';

-- Consultar Performance Schema
SELECT * FROM sys.statements_with_runtimes_in_95th_percentile;

-- Tablas más accedidas
SELECT * FROM sys.io_global_by_file_by_bytes;

-- Eventos de espera más comunes
SELECT * FROM sys.wait_classes_global_by_avg_latency;

Documentar el esquema

Un esquema bien documentado acelera la incorporación de nuevos miembros y facilita el mantenimiento.

SQL
-- Usar COMMENT en tablas y columnas
CREATE TABLE pedidos (
    id INT AUTO_INCREMENT PRIMARY KEY COMMENT 'Identificador único del pedido',
    usuario_id INT NOT NULL COMMENT 'FK a usuarios.id del cliente que realizó el pedido',
    total DECIMAL(10,2) NOT NULL COMMENT 'Monto total del pedido antes de impuestos',
    estado ENUM('pendiente', 'pagado', 'enviado', 'entregado', 'cancelado')
        NOT NULL DEFAULT 'pendiente' COMMENT 'Estado actual del pedido',
    creado_en DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT 'Fecha y hora de creación'
) COMMENT='Tabla que almacena los pedidos realizados por los clientes';

-- Ver comentarios
SHOW FULL COLUMNS FROM pedidos;
SHOW TABLE STATUS WHERE Name = 'pedidos';

Planificar antes de codificar. Invertir tiempo en diseñar el esquema, elegir los tipos de datos y definir los índices al inicio del proyecto evita dolores de cabeza cuando la base de datos crece. Un mal diseño es costosísimo de revertir en producción.
