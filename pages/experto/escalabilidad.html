Escalabilidad y alta disponibilidad

A medida que una aplicación crece, la base de datos suele convertirse en el cuello de botella. Diseñar para escalabilidad y alta disponibilidad desde el principio evita costosas reestructuraciones y garantiza que el servicio se mantenga operativo ante picos de tráfico o fallos.

Escalabilidad vertical vs horizontal

La escalabilidad vertical (scale up) consiste en añadir más recursos al mismo servidor: más RAM, CPU o almacenamiento. Es sencilla pero tiene un límite físico y suele ser costosa. La escalabilidad horizontal (scale out) distribuye la carga entre múltiples servidores más pequeños, lo que ofrece mayor capacidad teórica y tolerancia a fallos.

CaracterísticaVertical (Scale Up)Horizontal (Scale Out)
ImplementaciónSimple: más recursos al mismo equipoCompleja: requiere balanceador, replicación, sharding
LímiteCapacidad máxima del hardwareTeóricamente ilimitado (agregando nodos)
Tolerancia a fallosPunto único de falloAlta: si un nodo cae, los demás continúan
Costo incrementalCreciente (hardware high-end es caro)Lineal (servidores estándar económicos)
Complejidad operativaBajaAlta: monitoreo, sincronización, rebalanceo

Sharding

Sharding (fragmentación) divide los datos horizontalmente en fragmentos independientes llamados shards. Cada shard contiene un subconjunto de los datos y se ejecuta en un servidor distinto. Las estrategias comunes son:

SQL (conceptual)
-- Sharding por rango: usuarios 1-10000 en shard A, 10001-20000 en shard B
-- La aplicación decide a qué shard consultar según el id

-- Sharding por hash: función hash sobre el id para distribuir uniformemente
-- shard = HASH(id) % N (donde N es el número de shards)

-- Sharding por lista: agrupa por región geográfica
-- Tabla usuarios_américa, usuarios_europa, usuarios_asia

-- Ejemplo conceptual con particionamiento en MySQL
CREATE TABLE usuarios (
    id INT NOT NULL,
    nombre VARCHAR(100),
    region VARCHAR(20) NOT NULL
)
PARTITION BY LIST COLUMNS(region) (
    PARTITION p_america VALUES IN ('Norteamérica', 'Sudamérica'),
    PARTITION p_europa VALUES IN ('Europa', 'África'),
    PARTITION p_asia VALUES IN ('Asia', 'Oceanía')
);

Balanceo de carga

Un balanceador de carga de base de datos distribuye las conexiones entre varios servidores MySQL para repartir la carga de lectura y proporcionar tolerancia a fallos.

Configuración (ProxySQL)
-- ProxySQL: proxy de alto rendimiento para MySQL
-- Configurar servidores backend
INSERT INTO mysql_servers (hostgroup_id, hostname, port) VALUES
(0, '192.168.1.10', 3306),  -- Escritura principal
(1, '192.168.1.11', 3306),  -- Réplica de lectura 1
(1, '192.168.1.12', 3306);  -- Réplica de lectura 2

-- Reglas de enrutamiento: escrituras al hostgroup 0, lecturas al 1
INSERT INTO mysql_query_rules (active, match_pattern, destination_hostgroup)
VALUES (1, '^SELECT', 1),   -- Lecturas a réplicas
       (1, '.*', 0);        -- Todo lo demás al primario

-- MySQL Router (oficial de Oracle)
-- mysqlrouter --bootstrap root@192.168.1.10:3306 --user=mysqlrouter

Clustering

MySQL ofrece Group Replication para crear clústeres con consistencia fuerte. InnoDB Cluster simplifica la configuración mediante MySQL Shell y MySQL Router.

SQL
-- Group Replication: configuración en cada nodo
-- Nodo 1 (primario)
SET GLOBAL group_replication_bootstrap_group=ON;
START GROUP_REPLICATION;
SET GLOBAL group_replication_bootstrap_group=OFF;

-- Nodos 2 y 3 (secundarios)
START GROUP_REPLICATION;

-- Ver miembros del grupo
SELECT * FROM performance_schema.replication_group_members;

Alta disponibilidad (HA)

La alta disponibilidad garantiza que el servicio de base de datos continúe funcionando incluso si un servidor falla. Las estrategias incluyen failover automático, monitoreo de latidos y direcciones IP virtuales.

Keepalived (Linux)
# Configuración de keepalived para IP virtual MySQL
vrrp_instance VI_1 {
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 100
    virtual_ipaddress {
        192.168.1.100/24  # IP virtual que flota entre nodos
    }
    track_script {
        chk_mysql
    }
}

El sharding añade una complejidad operativa significativa: las consultas entre shards son lentas o imposibles, el rebalanceo requiere planificación y las transacciones distribuidas son costosas. Antes de fragmentar, agota todas las opciones de optimización vertical, índices, caching y replicación.

Ejemplo: arquitectura escalable completa

Una arquitectura típica para alta disponibilidad y escalabilidad combina varias técnicas:

Arquitectura
Clientes
    |
    v
ProxySQL / MySQL Router  (balanceo de carga, enrutamiento R/W)
    |
    +---> MySQL Primario  (escrituras)
    |         |
    |         +---> Réplica 1 (lectura asíncrona)
    |         +---> Réplica 2 (lectura asíncrona)
    |
    +---> Shard A (usuarios 1-50000)
    +---> Shard B (usuarios 50001-100000)
    
    Cada nodo del clúster con:
    - Keepalived para IP virtual
    - Monitoreo con PMM (Percona Monitoring and Management)
    - Backup automático con mysqldump o XtraBackup
