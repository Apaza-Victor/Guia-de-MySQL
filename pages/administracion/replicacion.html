Replicación en MySQL

La replicación permite copiar datos de un servidor MySQL maestro a uno o más servidores esclavos. Es la base para lograr alta disponibilidad, balanceo de lecturas y tolerancia a fallos en entornos de producción.

¿Qué es la replicación maestro-esclavo?

En el modelo maestro-esclavo, el servidor maestro registra todos los cambios en su binary log (binlog). Los esclavos se conectan al maestro, leen el binlog y aplican los mismos cambios en sus propias bases de datos, manteniéndose así sincronizados con el maestro.

Componentes de la replicación

Cada replicación involucra varios elementos que trabajan en conjunto para garantizar la sincronización de datos:

ComponenteDescripción
MaestroServidor principal que acepta escrituras y registra cambios en el binlog
EsclavoServidor réplica que recibe y aplica los cambios del maestro
BinlogArchivo binario donde se almacenan todas las modificaciones de datos
Relay logArchivo en el esclavo que almacena los eventos recibidos del maestro antes de aplicarlos
IO threadHilo del esclavo que se conecta al maestro y descarga el binlog al relay log
SQL threadHilo del esclavo que lee el relay log y ejecuta las sentencias en la base local
CHANGE MASTER TOSentencia que configura la conexión del esclavo hacia el maestro

Ventajas de la replicación

Implementar replicación en un entorno MySQL ofrece múltiples beneficios que mejoran tanto el rendimiento como la disponibilidad del sistema:

  • Balanceo de lecturas: las consultas SELECT pueden dirigirse a los esclavos, reduciendo la carga del maestro.
  • Alta disponibilidad: si el maestro falla, se puede promover un esclavo a maestro para minimizar el tiempo de inactividad.
  • Backups sin interrupción: se pueden realizar copias de seguridad en un esclavo sin afectar al servidor principal.
  • Distribución geográfica: los esclavos pueden ubicarse en distintas regiones para acercar los datos a los usuarios.

Configuración básica

Para configurar la replicación es necesario modificar los archivos de configuración del maestro y del esclavo, y luego establecer la conexión con CHANGE MASTER TO.

bash
# En el maestro: /etc/mysql/my.cnf
[mysqld]
server-id = 1
log_bin = /var/log/mysql/mysql-bin.log
binlog_do_db = mi_bd
bash
# En el esclavo: /etc/mysql/my.cnf
[mysqld]
server-id = 2
relay-log = /var/log/mysql/mysql-relay-bin.log
log_bin = /var/log/mysql/mysql-bin.log
read_only = 1
SQL
-- En el maestro: crear usuario para replicación
CREATE USER 'replicador'@'%' IDENTIFIED BY 'replica_pass';
GRANT REPLICATION SLAVE ON *.* TO 'replicador'@'%';
FLUSH PRIVILEGES;
SQL
-- En el esclavo: configurar la conexión al maestro
CHANGE MASTER TO
  MASTER_HOST = '192.168.1.10',
  MASTER_USER = 'replicador',
  MASTER_PASSWORD = 'replica_pass',
  MASTER_LOG_FILE = 'mysql-bin.000001',
  MASTER_LOG_POS = 107;

-- Iniciar la replicación
START SLAVE;

-- Verificar el estado
SHOW SLAVE STATUS\G;

La replicación en MySQL es asíncrona por defecto, lo que significa que el esclavo puede tener un ligero retraso respecto al maestro. Esto se conoce como consistencia eventual. Evalúa si tu aplicación puede tolerar lecturas ligeramente desactualizadas antes de implementar réplicas de solo lectura.
