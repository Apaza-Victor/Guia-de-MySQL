Normalización de bases de datos

La normalización es un proceso que elimina redundancias y anomalías en los datos mediante la aplicación de reglas llamadas formas normales (FN). Cada forma normal tiene requisitos más estrictos que la anterior. Trabajaremos con un ejemplo de una tabla pedidos desnormalizada y la iremos transformando paso a paso.

Tabla desnormalizada (0FN)

Partimos de una tabla única que almacena pedidos, clientes y productos todo junto:

id_pedidoclienteemailproductospreciostotal
1Ana Lópezana@mail.comLaptop, Mouse15000, 30015300
2Carlos Ruizcarlos@mail.comTeclado800800
3Ana Lópezana@mail.comMonitor45004500

Problemas: valores multivaluados en productos y precios, redundancia de datos de cliente, dependencias funcionales no triviales.

Primera forma normal (1FN)

Una tabla está en 1FN si todos sus atributos contienen valores atómicos (indivisibles) y cada columna tiene un único valor por fila.

id_pedidoclienteemailproductopreciototal
1Ana Lópezana@mail.comLaptop1500015300
1Ana Lópezana@mail.comMouse30015300
2Carlos Ruizcarlos@mail.comTeclado800800
3Ana Lópezana@mail.comMonitor45004500

Aún hay redundancia: los datos del cliente (cliente, email) y el total se repiten para cada fila del mismo pedido.

Segunda forma normal (2FN)

Una tabla está en 2FN si está en 1FN y todos los atributos no clave dependen de la totalidad de la clave primaria (sin dependencias parciales). Nuestra clave compuesta es (id_pedido, producto). cliente y email dependen solo de id_pedido, no de producto. Separamos:

2Carlos Ruizcarlos@mail.com800
3Ana Lópezana@mail.com4500

Tercera forma normal (3FN)

Una tabla está en 3FN si está en 2FN y no existen dependencias transitivas (un atributo no clave depende de otro atributo no clave). En la tabla pedidos, email depende de cliente, no directamente de id_pedido. Separamos cliente en su propia tabla:

Forma Normal de Boyce-Codd (BCNF)

BCNF es una versión más estricta de 3FN: toda dependencia funcional X → Y debe tener a X como superclave. Nuestro diseño ya cumple BCNF si cada determinante es una clave candidata. En la tabla detalle_pedido la clave (id_pedido, producto) es superclave y no hay dependencias anómalas.

SQL
CREATE TABLE cliente (
    id_cliente INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL
);

CREATE TABLE pedido (
    id_pedido INT AUTO_INCREMENT PRIMARY KEY,
    id_cliente INT NOT NULL,
    total DECIMAL(10,2) NOT NULL,
    fecha DATE NOT NULL,
    FOREIGN KEY (id_cliente) REFERENCES cliente(id_cliente)
);

CREATE TABLE detalle_pedido (
    id_detalle INT AUTO_INCREMENT PRIMARY KEY,
    id_pedido INT NOT NULL,
    producto VARCHAR(100) NOT NULL,
    precio DECIMAL(10,2) NOT NULL,
    cantidad INT DEFAULT 1,
    FOREIGN KEY (id_pedido) REFERENCES pedido(id_pedido)
);

No siempre conviene normalizar al máximo. En sistemas con altas cargas de lectura (reportes, dashboards) una desnormalización controlada puede mejorar el rendimiento al evitar JOINs costosos. Evalúa el equilibrio entre integridad y velocidad según tu caso de uso.
